**Purpose:** Repair an Owner-reported HTTP 503 when signing in as `MommaBee` while the associated email identifier succeeds.

## Findings

1. Owner username `MommaBee` exists, maps to the existing Auth account, is not banned, and has a verified email.
2. Cloudflare Pages production project `mommabees-website` points to the expected Supabase project and has an `SUPABASE_SECRET_KEY` secret binding configured; its masked value cannot be independently confirmed.
3. Prior server implementation resolved username → user UUID through a privileged PostgREST RPC, then separately fetched the Auth email through `/auth/v1/admin/users/{id}`. The latter extra request introduced a failure point on the username path only.
4. The generic `Sign-in temporarily unavailable` response is generated by the Pages login function on exceptions. The precise live exception was not independently captured; the architecture change removes the extra Auth Admin GET.
5. The browser's email/password login path, single-use CAPTCHA, user account, account ID, and role checks are unchanged.

## Implemented repair

**Migration:** `supabase/migrations/20261026_username_email_server_lookup_v115.sql`  
**New RPC:** `public.bakery_login_email(text)`, `SECURITY INVOKER`, service-role-only EXECUTE.  
**Privileged helper:** `bakery_private.login_email_by_username(text)`, `SECURITY DEFINER`, located in a non-exposed schema and executable only by `service_role`. It joins the profile's UUID to the canonical Auth user and returns email only to the server RPC.  
**Server code:** `functions/_lib/username-auth.js` now calls the one restricted RPC and no longer requests Auth Admin user details.  
**Tests:** `tests/source.test.js` includes the new lookup flow, absence of the unnecessary Auth Admin request, generic failures for unknown username and incorrect password, and CAPTCHA usage.
